# 🚀 RFC & Architecture Specification: Two-Tier Just-In-Time (JIT) Audio Stream Resolution

## 1. Executive Summary

This document outlines the architectural refactoring of the **MusicAre Audio Source Subsystem** to migrate from upfront multi-candidate stream extraction to a decoupled, two-tier **Just-In-Time (JIT) "Candidate & Stream"** resolution pattern (inspired by modern media clients such as Spotube, NewPipe, and LibreTube).

### Core Goals:
* **Drastic Latency Reduction**: Cut initial track playback startup time from **3.5–5.0 seconds down to ~1.0–1.2 seconds**.
* **Hardware & Network Efficiency**: Eliminate concurrent background thread execution and heavy multi-URL extraction on mobile devices, cutting CPU/battery consumption and avoiding IP rate-limiting (HTTP 429 Too Many Requests).
* **Enhanced User Experience**: Upgrade `AudioSourceBottomSheet` to display authentic provider metadata (e.g. real YouTube video title, channel/artist name if available, and duration) rather than generic "Candidate #1" labels.
* **Lean & Clean Plugin Interface**: Unify the candidate model using `CandidateTrack` (with `title` as mandatory, and `artist` and `duration_ms` as optional), discarding unnecessary payload bloat like thumbnails.

---

## 2. Problem Statement (Current Bottleneck)

In the current design, when `music_are` requests a stream for a track, the audio source plugin (`yt-dlp` in YouTube plugin):
1. Performs a fast text search query (`ytsearch5`) returning candidate metadata (~0.4s).
2. Ranks candidates using `TrackMatcher` heuristics (~0.01s).
3. Spawns multi-threaded worker pools to download web pages, execute JavaScript players, and decipher stream formats for **up to 4 candidates in parallel** (~3.0–4.5s).

### Why this is inefficient:
* **The 99% Rule**: In 99% of playback requests, candidate #1 plays flawlessly. Extracting 3 additional streams upfront penalizes every single track play for an edge case that rarely occurs.
* **Rate-Limit Exposure**: Making 4 simultaneous extraction queries to third-party endpoints triggers anti-bot mechanisms.
* **Opaque UI**: The client only receives raw `AudioStreamResponse` items (URL, bitrate, codec). The UI cannot tell the user *what* video or release is being played (e.g. "Official Video" vs "Live at Wembley").

---

## 3. The Two-Tier "Candidate & Stream" Architecture

Instead of treating audio source resolution as a single monolithic step, the process is decoupled into two clean domain concepts:

```text
┌──────────────────────────────────────────────────────────────────────────┐
│                         1. CANDIDATE SEARCH PHASE                        │
│               Search & rank platform candidate metadata                  │
│               (Fast, lightweight, no audio stream parsed)                │
│                                                                          │
│  Input: Track (Metadata: Title, Artist, Album, Duration)                 │
│  Output: List<CandidateTrack> (id, title, artist?, duration_ms?)         │
│  Latency: ~0.3s - 0.4s                                                   │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     │
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                            2. STREAM PHASE                               │
│               Resolve playable CDN URL for a single candidate            │
│               (Executed Just-In-Time only for the chosen item)           │
│                                                                          │
│  Input: candidate_id (Opaque Provider Identifier), AudioQuality          │
│  Output: AudioStreamResponse (Direct playable URL, headers, bitrate)     │
│  Latency: ~0.7s - 0.8s                                                   │
└──────────────────────────────────────────────────────────────────────────┘
```

### The Opaque Token Principle
* The `id` in `CandidateTrack` is an **opaque token** generated by the plugin.
* To the host application, the `id` is a transparent handle:
  * YouTube plugin: `id = "fJ9rUzIMcZQ"` (video ID)
  * SoundCloud plugin: `id = "12345678"` (track ID or permalink)
  * Jellyfin plugin: `id = "item_88192"` (server library GUID)
  * Local storage plugin: `id = "/storage/emulated/0/Music/song.mp3"` (file path)
* The host app never parses or validates the string: it simply passes it back to the plugin when requesting a stream for that candidate.

## 4. Domain Contracts & API Specifications

### 4.1. Python Plugin SDK (`musicare_plugin_sdk`)

#### Domain Models (`types.py` & `matcher.py`):
```python
@dataclass
class CandidateTrack:
    id: str                                  # Opaque platform identifier
    title: str                               # Video title, track title, or filename
    artist: Optional[str] = None             # Channel, artist, or uploader (optional)
    duration_ms: Optional[int] = None        # Duration if known (optional)

@dataclass
class ResolvedTrackPlayback:
    stream: AudioStreamResponse              # Playable stream for immediate playback
    candidates: List[CandidateTrack]         # Candidate list for switcher/fallback
    active_candidate_id: str                 # ID of currently playing candidate
```

#### Plugin Contract (`base_plugin.py`):
```python
class BaseAudioSourcePlugin(ABC):
    @property
    @abstractmethod
    def id(self) -> str: ...

    @property
    @abstractmethod
    def name(self) -> str: ...

    @property
    @abstractmethod
    def version(self) -> str: ...

    @abstractmethod
    def search_candidates(self, track: Track) -> List[CandidateTrack]:
        """Search platform and return lightweight metadata candidates (fast: < 0.4s)."""
        pass

    @abstractmethod
    def resolve_stream(self, candidate_id: str, quality: AudioQuality) -> AudioStreamResponse:
        """Extract direct audio stream URL for a specific candidate_id (~0.7s)."""
        pass
```

### 4.2. Host Daemon RPC (`musicare_python_host_runtime / engine.py`)

The embedded CPython Flask daemon exposes two dedicated, single-responsibility endpoints:

1. **`POST /resolve_track` (Initial Track Playback)**
   * **Request**:
     ```json
     {
       "track": { "name": "Bohemian Rhapsody", "artists": [{"name": "Queen"}], "durationMs": 354000 },
       "quality": "high"
     }
     ```
   * **Execution**: Executes `candidates = plugin.search_candidates(track)`, ranks them via `TrackMatcher`, calls `plugin.resolve_stream(candidates[0].id, quality)`, and returns the composite payload.
   * **Response (HTTP 200)**:
     ```json
     {
       "active_candidate_id": "fJ9rUzIMcZQ",
       "stream": {
         "url": "https://rr1---sn...googlevideo.com/...",
         "quality": "high",
         "codec": "m4a",
         "bitrate": 160000,
         "expires_at": 1750000000000,
         "headers": { "User-Agent": "..." }
       },
       "candidates": [
         { "id": "fJ9rUzIMcZQ", "title": "Queen – Bohemian Rhapsody (Official Video)", "artist": "Queen Official", "duration_ms": 359000 },
         { "id": "vsl3gBVO2k4", "title": "Bohemian Rhapsody (Live at Wembley)", "artist": "Live Archive", "duration_ms": 380000 }
       ]
     }
     ```
   * **Latency**: ~1.1s – 1.2s total (single HTTP round-trip).

2. **`POST /resolve_stream` (Manual Switch or Automatic Failover)**
   * **Request**:
     ```json
     {
       "candidate_id": "vsl3gBVO2k4",
       "quality": "high"
     }
     ```
   * **Execution**: Calls `plugin.resolve_stream(candidate_id, quality)` directly without re-searching.
   * **Response (HTTP 200)**: Returns purely `AudioStreamResponse` (no dummy lists or empty arrays).
   * **Latency**: ~0.7s total.

### 4.4. Flutter App (`music_are`)

#### Data Layer (`PlaybackCandidates`):
```dart
@immutable
class PlaybackCandidates {
  final List<CandidateTrack> candidates;
  final AudioStreamResponse? activeStream;
  final String? activeCandidateId;

  const PlaybackCandidates({
    this.candidates = const [],
    this.activeStream,
    this.activeCandidateId,
  });

  bool get isEmpty => candidates.isEmpty;
  int get count => candidates.length;

  CandidateTrack? get currentCandidate =>
      candidates.where((c) => c.id == activeCandidateId).firstOrNull;

  CandidateTrack? get nextCandidate {
    final idx = candidates.indexWhere((c) => c.id == activeCandidateId);
    if (idx >= 0 && idx + 1 < candidates.length) {
      return candidates[idx + 1];
    }
    return null;
  }
}
```

#### Presentation Layer (`CandidatesState` & `AudioSourceBottomSheet`):
* The bottom sheet displays `candidate.title` (primary title) and `candidate.artist` (channel or uploader, if present).
* Tapping an alternative candidate invokes `player.selectStreamCandidate(candidate.id)`.
* `AudioPlayerService` calls `_client.resolveStream(candidateId)` in ~0.7s, switches audio playback, and updates the active candidate badge.

## 5. End-to-End Operational Flows

### Flow A: Initial Playback (Cold Start)
1. User taps "Play" on track *Come Together*.
2. `AudioPlayerService` requests `client.resolveTrack(title, artists, durationMs)`.
3. Python host runs `search_candidates` (0.4s) -> picks candidate #0 -> runs `resolve_stream` (0.7s).
4. Python returns `ResolvedTrackPlayback` (Stream + Candidate list) in **1.1s**.
5. Flutter immediately feeds `stream.url` to `just_audio` and displays playback UI.

### Flow B: User Switches Audio Source Manually
1. User opens `AudioSourceBottomSheet`.
2. User sees real titles: *Come Together (Remastered)*, *Come Together (Live at Shea Stadium)*.
3. User taps candidate #2 (`id: abc987`).
4. Flutter calls `client.resolveStream(candidateId: "abc987")`.
5. Python skips searching and extracts the URL for `abc987` directly in **0.7s**.
6. Playback resumes on the new stream without reloading metadata.

### Flow C: Automatic Playback Failover
1. Candidate #1 stream returns HTTP 403 Forbidden or network drops.
2. `AudioPlayerService` catches the exception.
3. `candidates.nextCandidate` yields candidate #2 (`id: abc987`).
4. `AudioPlayerService` immediately requests `client.resolveStream(candidateId: "abc987")`.
5. Music starts on the fallback stream in **0.7s**.
